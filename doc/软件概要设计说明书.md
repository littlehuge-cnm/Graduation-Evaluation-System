# 本科生毕业设计评价系统概要设计说明书

## 1 引言

软件概要设计主要是一个把软件需求转化为软件表示的过程，这种表示只是描述出软件总的概貌。

### 1.1 编写目的

概要设计说明书编制的目的是：说明对程序系统的设计考虑，包括程序系统的基本处理流程、程序系统的组织结构、模块划分、功能分配、接口设计、运行设计、数据结构设计和出错处理设计等，为程序的详细设计提供基础。

本软件概要说明书的读者是系统开发人员或合同约定的人员。

### 1.2 背景

（1）本系统的名称是：本科生毕业设计评价系统。

（2）本项目的任务提出者是软件工程综合实训任务书（2026），开发者是实训小组，用户是高校毕业设计管理人员、教师和学生，实现该软件的环境是基于 Web 的 B/S 架构系统。

（3）本系统能为学校教务管理提供毕业设计全过程的成绩与评语数据。

### 1.3 定义

B/S：Browser/Server，浏览器/服务器架构。

RBAC：Role-Based Access Control，基于角色的访问控制。

GDES：Graduation Design Evaluation System，本科生毕业设计评价系统。

FreeMarker：一种模板引擎，用于生成 Word 文档。

JWT：JSON Web Token，用于登录鉴权。

## 2 总体设计

### 2.1 需求规定

本系统的功能划分为如下几个部分。

（1）用户与基础数据管理：主要是对系统用户进行管理，包括超级管理员、教师、学生的登录、退出、操作记录等，以及学生信息、教师信息、班级、专业等基础数据的维护。

（2）分组与对应关系管理：主要是对教师分组（每组 3 人，含组长、秘书、成员各 1）、学生分组以及各环节教师组与学生组对应关系进行管理。

（3）指导关系管理：主要是建立指导教师与学生、评阅教师与学生之间的对应关系。

（4）任务书与指导书管理：指导教师在线填写任务书和指导书，学生查看。

（5）开题环节管理：组长录入开题成绩，指导教师录入外文翻译成绩。

（6）中期检查环节管理：组长录入中期检查成绩与评语。

（7）评阅与指导评语管理：指导教师填写评语和建议成绩，评阅教师填写评语和成绩。

（8）答辩环节管理：秘书录入答辩记录，组长录入答辩小组成绩与评语，答辩委员会评定等级和评语。

（9）评价手册导出：按学生导出"学生姓名.docx"，包含全部十项内容并显示签名。

本系统对性能的规定为：

（1）系统要求输入的成绩为 0~100 的数值；

（2）系统的更新处理时间应该在可接受的范围内；

（3）系统的数据查询时间应该在可接受的范围内；

（4）系统的数据统计时间应该在可接受的范围内；

（5）操作方式上应该能够满足鼠标和键盘任意切换的需要；

（6）能够支持主流浏览器（Chrome、Edge、Firefox）的运行环境；

（7）留有同学校教务系统对接的接口。

### 2.2 运行环境

（1）硬件环境：运行本软件的服务器端要求处理器性能良好（建议多核 CPU），内存在 8 GB 以上，硬盘剩余空间 100 GB 以上的计算机；客户端为能够运行主流浏览器的台式机或笔记本，处理器在奔腾 III 以上、内存在 4 GB 以上即可。

（2）软件环境：本系统支持的操作系统包括 Windows Server 2016 及以上、Linux（CentOS 7/Ubuntu 18.04 及以上）；本系统的支持数据库为 MySQL 8.0+；本软件的开发工具与运行环境为 JDK 17、Spring Boot、Tomcat Web 服务器、前端 Vue 框架、FreeMarker 模板引擎。

### 2.3 基本设计概念和处理流程

本系统采用 B/S 架构，前后端分离，后端基于 Spring Boot 提供 RESTful API，前端基于 Vue 框架构建页面，数据持久化采用 MySQL 数据库。系统通过 RBAC 模型对超级管理员、教师、学生三类用户进行权限控制，教师身份依据分组关系自动判定为组长、秘书、指导教师、评阅教师等多种身份。

本系统的总体处理流程如下：

（1）超级管理员建立基础数据（学生、教师、班级、专业等）。

（2）超级管理员进行教师分组和学生分组，并设定各环节的对应关系。

（3）超级管理员设定指导教师-学生、评阅教师-学生对应关系。

（4）指导教师填写任务书和指导书。

（5）开题环节：组长录入开题成绩，指导教师录入外文翻译成绩。

（6）中期检查环节：组长录入中期检查成绩与评语。

（7）指导教师填写指导评语和建议成绩，评阅教师填写评阅评语和成绩。

（8）答辩环节：秘书录入答辩记录，组长录入答辩小组成绩与评语。

（9）答辩委员会（超级管理员）给出评定等级和评语。

（10）所有环节结束后，导出"学生姓名.docx"评价手册。

各环节 IPO 表不再一一列出。

### 2.4 结构

本系统的软件结构按功能划分为以下层次：

（1）表示层：登录页、超管后台（基础数据/分组/对应关系/答辩委员会）、教师工作台（任务书/指导书/各环节录入）、学生信息查看页、评价手册导出页。

（2）业务逻辑层：用户管理模块、基础数据管理模块、分组管理模块、指导关系管理模块、任务书管理模块、开题管理模块、中期检查管理模块、评阅管理模块、答辩管理模块、评价手册导出模块、权限校验模块。

（3）数据访问层：通过 MyBatis/JPA 等持久层框架访问数据库。

所有模块都必须调用"权限校验"模块进行身份验证和权限过滤，只有合法用户且具备相应权限才能使用对应功能。

本系统的软件结构图参见图 1，其他模块之间的关系在此不再一一说明。

### 2.5 功能需求与程序的关系

用户身份验证必须调用"权限校验"模块程序进行身份验证，登录后根据不同用户角色（超级管理员、教师、学生）及其身份上下文（指导教师、评阅教师、组长、秘书）调用不同的功能模块。

各功能与程序的调用关系如下：

| 功能模块 | 调用的程序模块 |

| 基础数据维护 | 基础数据管理模块 |
| 分组与对应关系 | 分组管理模块 |
| 指导/评阅关系 | 指导关系管理模块 |
| 任务书/指导书 | 任务书管理模块 |
| 开题成绩录入 | 开题管理模块 |
| 中期检查录入 | 中期检查管理模块 |
| 指导/评阅评语 | 评阅管理模块 |
| 答辩记录与成绩 | 答辩管理模块 |
| 评价手册导出 | 评价手册导出模块 |

### 2.6 人工处理过程

本软件系统的工作过程中，开题打分、纸质论文评阅、答辩现场提问等环节需要人工处理后由相应角色将结果录入系统；其余流程均由系统自动处理。

### 2.7 尚未解决的问题

与学校教务系统的数据对接（自动同步学生、教师基础信息）是本系统尚未解决而设计者认为在系统完成之前必须解决的问题。

## 3 接口设计

### 3.1 用户接口

本系统采用 Web 浏览器图形界面作为人机接口，如使用窗口、菜单、对话框、表单、Toast 提示等，支持响应式布局，操作反馈采用 Toast 提示，错误信息明确，表单输入需有必填、格式、范围校验。

### 3.2 外部接口

本系统支持处理器在奔腾 III 以上、内存在 4 GB 以上的客户端计算机；支持主流浏览器（Chrome、Edge、Firefox 最新版本）；支持 MySQL 8.0+ 关系数据库；预留与学校教务系统对接的 RESTful API（获取学生、教师基础信息）；支持 Excel/CSV 文件批量导入学生、教师信息。

### 3.3 内部接口

"权限校验"模块：提供系统用户登录时的身份验证功能，用户进行角色切换时必须调用此模块进行身份验证，并根据用户角色及身份上下文对数据和操作进行过滤。

本系统前后端通过 RESTful API 通信，数据格式为 JSON，推荐使用 JWT 进行登录鉴权。Word 导出基于 FreeMarker 模板引擎接口。

本系统内元素接口的安排在此不再一一描述。

## 4 运行设计

### 4.1 运行模块组合

不同的用户登录此系统获得的系统功能是不同的，如超级管理员具有系统的全部功能，教师根据其身份（指导教师/评阅教师/组长/秘书）只能访问对应的功能模块，学生只能查看本人信息。更多的描述不再一一列出。

### 4.2 运行控制

超级管理员对系统的其他用户设置系统功能的访问权限，并根据分组关系自动判定教师的身份上下文，这样权限受限的用户就只能访问部分系统模块。环节间存在严格先后次序，前一环节未完成不能进入下一环节，由系统自动控制。更多的描述不再一一列出。

### 4.3 运行时间

"权限校验"模块在完成用户登录的身份验证后立即退出运行，释放占用的系统资源。Word 导出模块在生成文档并完成下载后释放资源。其他模块说明仿此说明。

## 5 系统数据结构设计

### 5.1 逻辑结构设计要点

本系统的主要实体包括：学生、教师、超级管理员、教师组、学生组、组对应关系、指导关系、评阅关系、任务书、指导书、开题成绩、外文翻译成绩、中期检查、指导评语、评阅评语、答辩记录、答辩小组成绩、答辩委员会评定、操作日志等。

实体间的主要关系为：

（1）一名教师可指导多名学生，一名学生只有一名指导教师（1:n）。

（2）一名教师可评阅多名学生，一名学生只有一名评阅教师（1:n），且评阅教师 ≠ 指导教师。

（3）一个教师组包含 3 名教师（1 名组长、1 名秘书、1 名普通成员）。

（4）一个学生组包含多名学生。

（5）每个环节中，教师组与学生组一一对应。

（6）一名学生在每个环节中有一条成绩/评语记录。

详细的 E-R 图与逻辑结构设计参见本书数据库设计部分。

### 5.2 物理结构设计要点

本系统采用 MySQL 8.0+ 关系数据库进行数据持久化存储。数据库表设计遵循最小化原则，在满足第三范式的基础上尽量合并同类实体。专业、班级、院系等基础信息直接以字符串字段存储于学生、教师表中，不再单独建表。各环节的成绩、评语、记录合并为统一的评价记录表，通过条目类型字段区分。任务书与指导书合并为文档表。指导关系与评阅关系合并为师生关系表。环节进度通过独立的环节状态表跟踪，支持未开始/进行中/已完成的状态流转。主键采用自增整数或业务编号（如学号、工号），外键通过应用层维护关联关系。

| score | 总成绩 | decimal | 5,2 | 各分项之和或加权总分，可空 |
| grade | 等级 | varchar | 10 | 优/良/中/及格/不及格，仅委员会评定填写 |
| comment | 评语/记录内容 | varchar | 2000 | 可空 |
| recorder_no | 录入人账号 | varchar | 20 | 非空（教师工号或管理员账号，签字时导出对应教师姓名） |
| record_time | 录入时间/答辩日期 | datetime | — | 非空 |
| update_time | 更新时间 | datetime | — | — |
| record_status | 记录状态 | varchar | 10 | 暂存/已确认，默认暂存 |

item_type 取值对应评价手册十项内容中的后八项，各分项及满分如下：

| item_type 取值 | 对应评价手册项 | 录入人 | 分项（满分） | 总满分 |
| --- | --- | --- | --- | --- |
| 开题成绩 | ③开题报告 | 组长 | 调研资料获取能力(4)、方案设计合理性(4)、开题报告规范性(4) | 12 |
| 外文翻译 | ④外文翻译成绩 | 指导教师 | 阅读理解能力(1)、专业词语准确性(1)、译文规范性(1) | 3 |
| 中期检查 | ⑤中期检查评语和成绩 | 组长 | 进度情况(5)、综合能力(5)、已完成质量(5) | 15 |
| 指导评语 | ⑥指导教师评语和建议成绩 | 指导教师 | 方案设计能力(3)、理论应用能力(3)、分析解决问题能力(3)、科学素养态度(3)、工作量与质量(3) | 15 |
| 评阅评语 | ⑦评阅教师评语和成绩 | 评阅教师 | 规范性与质量(4)、理论运用(4)、方案正确性(4)、创新性(3) | 15 |
| 答辩记录 | ⑧答辩记录 | 秘书 | 无分项，记录答辩日期、记录人、问答内容 | — |
| 答辩成绩 | ⑨答辩小组评定成绩和评语 | 组长 | 陈述情况(10)、设计水平(10)、工作量评价(10)、答辩情况(10) | 40 |
| 委员会评定 | ⑩答辩委员会评语和总评成绩/等级 | 超级管理员 | 加权总分=开题×12%+翻译×3%+中期×15%+指导×15%+评阅×15%+答辩×40% | 100 |

说明：sub_scores 字段按上表分项顺序以逗号分隔存储各项得分；score 字段对于前七项为各分项之和，对于委员会评定为加权总分。答辩记录（item_type='答辩记录'）无分项成绩，sub_scores 为空，答辩日期存于 record_time。各环节签字通过 recorder_no 关联 t_teacher 导出对应教师姓名。record_status 字段：录入时默认"暂存"，环节"进行中"期间可多次修改；录入人点击确认后变为"已确认"不可再改；环节标记"已完成"时所有未确认记录自动转为"已确认"；如需修改已确认记录，由超管解锁退回"暂存"。

#### 5.2.6 环节状态表

**（9）t_stage_status（环节状态表，跟踪每名学生在三个环节的进度）**

| 字段名 | 含义 | 类型 | 长度 | 约束 |
| --- | --- | --- | --- | --- |
| id | 记录编号 | int | — | 主键，自增 |
| student_no | 学号 | varchar | 20 | 外键，非空 |
| stage | 环节 | varchar | 10 | 取值：开题/中期/答辩，非空 |
| status | 状态 | varchar | 10 | 取值：未开始/进行中/已完成，非空，默认未开始 |
| start_time | 开始时间 | datetime | — | 进入"进行中"时写入 |
| complete_time | 完成时间 | datetime | — | 进入"已完成"时写入 |

说明：每名学生每个环节一条记录，(student_no, stage) 为唯一键。环节间存在严格先后次序，仅当"开题"状态为"已完成"时，"中期"方可由"未开始"进入"进行中"；仅当"中期"为"已完成"时，"答辩"方可进入"进行中"。状态流转由应用层校验与维护。

#### 5.2.8 状态字段汇总

系统共涉及 8 类状态字段，分布如下：

| 序号 | 状态名称 | 所属表 | 字段名 | 取值 |
| --- | --- | --- | --- | --- |
| 1 | 账号状态 | t_admin/t_teacher/t_student | account_status | 启用/禁用 |
| 2 | 学生整体进度 | t_student | overall_status | 待分配/进行中/待答辩/已完成/已弃做 |
| 3 | 教师分组状态 | t_teacher_group | group_status | 待启用/已启用/已停用 |
| 4 | 师生关系状态 | t_teacher_student | relation_status | 生效/已解除 |
| 5 | 文档状态 | t_document | status | 草稿/已提交 |
| 6 | 课题审批状态 | t_document（任务书） | approval_status | 待系审/系通过/系驳回/待院审/院通过/院驳回 |
| 7 | 评价记录状态 | t_score_record | record_status | 暂存/已确认 |
| 8 | 环节状态 | t_stage_status | status | 未开始/进行中/已完成 |

各状态流转规则如下：

（1）账号状态：默认启用，超管可禁用异常账号，禁用后无法登录但数据保留，可重新启用。

（2）学生整体进度：新增学生默认"待分配"；分配指导教师后自动变为"进行中"；所有成绩录入完毕后由超管标记为"待答辩"；委员会评定完成后变为"已完成"；学生放弃或延期由超管标记为"已弃做"。

（3）教师分组状态：创建默认"待启用"；超管启用后变为"已启用"方可设定环节对应关系；毕业设计周期结束后可停用。

（4）师生关系状态：默认"生效"；设计规定指导关系本周期内不再变更，仅教师离职等特殊情况由超管解除为"已解除"，历史成绩评语保留。

（5）文档状态：指导教师保存默认"草稿"，学生不可见；提交后变为"已提交"，学生可查看；已提交后如需修改由超管退回"草稿"。

（6）课题审批状态（仅任务书）：任务书提交后进入"待系审"；系主任（超管代行）通过后自动进入"待院审"；院长（超管代行）通过后课题正式生效为"院通过"；任一环节驳回需指导教师修改后重新提交。

（7）评价记录状态：录入时默认"暂存"，环节"进行中"期间可多次修改；录入人确认后变为"已确认"不可再改；环节标记"已完成"时所有未确认记录自动转为"已确认"；如需修改已确认记录由超管解锁退回"暂存"。

（8）环节状态：默认"未开始"；超管启动后变为"进行中"方可录入成绩；成绩录入完毕由组长或超管确认后变为"已完成"。严格先后次序：开题"已完成"→中期可启动；中期"已完成"且指导/评阅评语均填写→答辩可启动。

### 5.3 数据结构与程序的关系

本系统进行用户身份验证时，首先通过登录界面获得用户输入的用户账号和密码，程序通过持久层框架访问数据库的用户表（t_admin/t_teacher/t_student），若不匹配，返回结果到登录窗口，提示错误，相反登录成功。

成绩录入时，程序根据当前登录用户的工号及分组关系，自动筛选出本组（或自己指导/评阅）的学生名单，先查询 t_stage_status 表确认对应环节处于"进行中"状态（否则拒绝录入），再向 t_score_record 表插入对应 item_type 的记录，同时向 t_operation_log 表记录操作日志。环节所有成绩录入完成后，由组长或超管将 t_stage_status 中该环节状态置为"已完成"，下一环节方可进入"进行中"。

评价手册导出时，程序根据学号依次查询 t_document（任务书、指导书）和 t_score_record（按 item_type 区分开题成绩、外文翻译、中期检查、指导评语、评阅评语、答辩记录、答辩成绩、委员会评定）两张表的数据，通过 FreeMarker 模板渲染生成"学生姓名.docx"。

其他情况照此描述。

## 6 系统出错处理设计

### 6.1 出错信息

当用户没有输入非空字段而进行数据提交时，系统提示"××字段数据不得为空，请重新输入再提交"。

当成绩输入超出 0~100 范围时，系统提示"成绩必须在 0~100 之间"。

当用户尝试访问无权限的数据时，系统提示"您没有权限执行此操作"。

当环节未完成而尝试进入下一环节时，系统提示"前一环节尚未完成，无法进入下一环节"。

其他出错处理不再一一列出。

### 6.2 补救措施

本系统中，当用户没有输入非空字段而进行数据提交时，系统提示××字段数据不得为空，请重新输入再提交。此时输入界面保留刚刚输入信息的界面，而不是清空全部输入界面上的所有数据；要求用户重新输入。

本系统提供数据备份功能，方便用户对数据的备份；成绩修改日志记录修改前后的值，便于追溯和回滚。
